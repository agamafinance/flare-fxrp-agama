# Agama confidential YT market — a Flare Compute Extension

Agama's sealed-bid RFQ for yield tokens, rebuilt as a **Flare Compute Extension (FCE)** on
[Flare Confidential Compute](https://dev.flare.network/fcc/overview).

Fixed-rate products need a two-sided market: for a saver to lock certainty, someone must take the
variable yield (the YT). On a yield-poor chain that demand is thin, and market makers will not post
public quotes because an on-chain order book leaks their pricing and gets them picked off.

So the quotes never touch the chain. Each market maker signs its quote and sends it straight to the
enclave; the matching runs inside attested hardware; only the winning settlement comes out, signed,
for the contract to verify before it moves a single token.

Built from [`flare-foundation/fce-extension-scaffold`](https://github.com/flare-foundation/fce-extension-scaffold).

## How it works

```
market maker  ──POST /direct (RFQ/QUOTE)──▶  proxy ──▶  TEE ─┐
                 signed, optionally                          │  book in enclave memory
                 ECIES-sealed                                │
                                                             │
seller ──openRfq──▶ AgamaRfqInstructionSender (escrows YT)    │
       ──requestSettlement──▶ TeeExtensionRegistry ──▶ data providers ──▶ TEE
                                                             │
                                        best execution ──────┘
                                                │
                                   signed winning settlement
                                                │
anyone ──settle(result, sig)──▶ contract verifies the TEE signature, then pays
```

Two channels in, one out — the shape every FCE has:

| Direction | Channel | Carries |
|---|---|---|
| In, off-chain | `POST /direct` → proxy → TEE | `RFQ`/`QUOTE` — a sealed, MM-signed quote |
| In, on-chain | `requestSettlement` → registry → data providers → TEE | `RFQ`/`SETTLE` — run best execution on this RFQ |
| Out | TEE → proxy → relayer → chain | the signed winning settlement, verified in `settle` |

## What the design guarantees

- **Losing quotes never exist on chain.** They live in enclave memory and are dropped once the RFQ
  settles. The `/state` endpoint reports counts only — never a price, never a market maker.
- **Settlement is on-chain only, so the book cannot be read by anyone.** `SETTLE` is refused on the
  public `/direct` channel and accepted solely as an on-chain instruction from
  `requestSettlement`. Without this, an anonymous caller could `POST /direct` a `SETTLE` and get the
  winner, the price and a TEE signature for any open RFQ — a hole confirmed exploitable against an
  earlier build and closed in the enclave now running (a `/direct` `SETTLE` returns 403 before the
  book is computed). `QUOTE` stays on `/direct`; an on-chain quote only publishes the sender's own
  bid.
- **Nobody can quote for someone else.** Every quote is signed by its MM over `quoteDigest`, which
  binds the chain id, the RFQ contract, the RFQ id, the amount, the price and a deadline. The digest
  is pinned across all three languages by `test/vectors/quote_digest.json` (generated by the Python
  extension, replayed in the Solidity test, recomputed independently in the Go test runner).
- **The relayer cannot change the terms.** The extension reads seller, amount and reserve from the
  contract, not from whoever asked for a settlement.
- **The seller's floor is enforced on chain too.** `settle` re-checks `price >= minPrice`, so even a
  misbehaving enclave cannot sell the YT below the reserve.
- **Only a registered machine can settle.** `settle` requires the recovered signer to be a machine
  the `FlareTeeManager` lists as active (PRODUCTION) for this extension — a whitelisted code hash on
  attested hardware, checked against `getActiveTeeMachines`. An arbitrary key the contract owner
  might set is not a registered machine and cannot settle; an optional `teeAddress` can narrow this
  to one specific machine.
- **The oracle actually decides.** Every premium is valued in USD through FTSOv2 and must fall inside
  a per-settlement band; ties at equal price are broken with Flare Secure RNG. Both are read from
  inside the enclave through the ContractRegistry.
- **`settle` verifies attested code, not an operator.** The signature must come from the registered
  TEE machine, whose code hash is whitelisted on-chain for this extension and whose attestation is
  verified by Flare's data providers.

## Deploy to Coston2

Prerequisites: Docker, Go 1.25.1+, Foundry, `jq`, and a funded Coston2 key
([faucet](https://faucet.flare.network/coston2)).

**No Flare credentials needed.** The extension proxy reads FSP data — signing policies, voter
registrations, recent voting rounds — from a C-chain indexer database. Flare issues credentials to a
hosted one on request; `scripts/start-indexer.sh` runs the same
[open-source indexer](https://github.com/flare-foundation/flare-system-c-chain-indexer) locally
instead. In FSP mode it backfills that metadata from two reward epochs back and then follows the
head, so a cold start is a backfill, not a chain sync from genesis.

```bash
cp .env.example .env            # keys, FXRP_ADDR / YT_ADDR
./scripts/pre-build.sh          # deploy the RFQ, register the extension on chain
./scripts/start-indexer.sh      # our own C-chain indexer + its database
./scripts/start-services.sh     # redis + ext-proxy + the extension
./scripts/post-build.sh         # whitelist the code hash, register the TEE machine
./scripts/test.sh               # full sealed-bid round trip
```

That local run uses simulated attestation. Contrary to the scaffold's docs, FTDC accepts it —
Coston2's `getSystemSupportedPlatforms()` lists `TEST_PLATFORM`, and several extensions run machines
at PRODUCTION on it. Real attestation is a stronger claim, not an entry requirement. `scripts/deploy-gcp.sh` does that
in one shot: it builds the image with `MODE=0`, pushes it by digest, puts redis, the proxy and the
indexer on an ordinary VM, and runs the extension — and only the extension — on a GCP Confidential
Space VM (AMD SEV). Confirm what actually came up before registering it:

```bash
./scripts/deploy-gcp.sh --info
# platform GCP_AMD_SEV, and a codeHash that is NOT 0x194844cf… (that one is simulated)
```

Full lifecycle and the platform traps: [`docs/deployment-steps.md`](docs/deployment-steps.md).

Check the whole deployment against the chain in one command:

```bash
./scripts/verify-registration.sh
```

It prints the live node's view beside the `FlareTeeManager` record — machine id, proxy id, URL,
platform, code hash, instruction sender — and the machine status (2 = production). When
registration stalls, it says in one screen whether the fault is here or upstream.

**The indexer must stay within 60 seconds of the head, not merely catch up.** tee-proxy compares
the indexer's latest block against the chain and refuses to serve past a hardcoded 60-second
tolerance (`outOfSyncTolerance` in its `internal/proxy/proxy.go`). Two settings in
`config/indexer/config.coston2.toml` decide whether it stays inside that window:

- `new_block_check_millis = 200`. At the default `1000` the indexer advances about 0.7 blocks a
  minute slower than Coston2 produces them — roughly 40 blocks an hour — so it drifts for hours
  after it last looked healthy and then crosses the tolerance with nothing in the log to explain
  it. At `200` the lag holds at 8-15 seconds.
- `batch_size = 20`. This is also the DB commit size: rows land only when a batch fills, so the head
  the proxy reads lags by a whole batch. At `1000` that is roughly half an hour of chain, which can
  never come inside the tolerance at all.

Watch `select max(number) from blocks` against the chain head rather than the indexer's log — it
prints no progress line and no rate.

**A self-hosted indexer can pin the proxy to a stale signing policy.** Nothing says so:
`register-tee`'s pre-flight checks *Flare's* proxy policy, never yours. Compare them:

```bash
curl -s "$EXT_PROXY_URL/info"                  | jq .teeInfo.lastSigningPolicyId
curl -s https://tee-proxy-coston2-1.flare.rocks/info | jq .teeInfo.lastSigningPolicyId
```

Two settings keep them level, both already in this repo's config. The proxy runs
`initial_signing_policy_offset = 0`, not the scaffold's `2`: with an offset it boots `offset` epochs
back and has to climb one epoch at a time, and each climb needs that epoch's
`signNewSigningPolicy` transactions, which a self-hosted indexer's log-only pre-window backfill
never has. And the indexer collects that transaction explicitly — FSP mode hardcodes collectors for
Submission and Relay but not for `FlareSystemsManager.signNewSigningPolicy`, so without the extra
`[[indexer.collect_transactions]]` entry the proxy can never leave the epoch it booted on.

## Known limitations

- **Confidential Space has no durable storage.** The TEE key lives only in enclave memory, so
  restarting the VM mints a new machine address and a new signing key. That machine is unknown to
  the registry, so it has to be pre-registered again — `REGISTER_TEE_COMMAND=rRap ./scripts/post-build.sh`,
  where `r` pre-registers and `Rap` alone only works for a machine the registry already holds.
  `test.sh` re-points `setTeeAddress` at whatever the live proxy's `/info` reports, because a stale
  binding reverts `settle` on a bad TEE signature long after the confidential part of the run has
  already succeeded. The encrypted state-backup design used by `fce-orderbook` (TPM-sealed DEK plus
  off-site backup) is the fix for the state itself, and is not wired in here.
- **A stale machine record can still misroute an instruction — now bounded by `settle`.**
  `requestSettlement` routes to `getRandomTeeIds(extensionId, 1)` — a *random* machine among those
  at status 2. The TEE key is memory-only, so each rebuild mints a new machine address and leaves
  the old record at status 2 until it is paused. `settle` now accepts *any* machine the registry
  lists as active for the extension (not a single pinned address), so a result from whichever machine
  the draw picked still verifies — but a draw that lands on a machine whose node no longer exists
  returns no result at all. So stale records are still worth pausing with `pause(teeId)` on
  `FlareTeeManager` (there is no unpause, only `toProduction` with a fresh availability proof); the
  registry binding removes the *wrong-signer* failure, not the *dead-node* one.
- **The Python image is reproducible on the same machine only.** Cross-machine bit-for-bit builds —
  what lets an auditor reproduce the code hash themselves — need the Go path. That port is the
  natural follow-up; the wire contract and the fixtures are language-neutral, which is what makes it
  tractable.
- **Best execution covers the quotes the enclave holds.** A market maker that never reaches the proxy
  is not in the auction. The seller's on-chain reserve bounds the downside.
- **The Python framework did not handle direct actions.** tee-node forwards a direct action with the
  `DirectInstruction` envelope, where the payload sits under `message` rather than `originalMessage`;
  the scaffold's `base/server.py` parsed it as a `DataFixed`, which succeeds and yields an empty
  payload. Fixed here (`parse_direct_instruction`) and pinned by tests — worth upstreaming.
- **`teeAddress` is owner-set.** It should match a machine registered for this extension; the minimal
  registry interface cannot enumerate them, so `test.sh` derives it from the live proxy's `/info`
  rather than from stored state, and the owner sets it.
